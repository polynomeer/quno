# Phase 91 — 에이전트 소비 가설 검증 실험 설계

[ADR-0069](../architecture/decisions/0069-agent-era-positioning-verified-fix-memory.md)의 포지셔닝("증거가 붙은 해결 기록소 + AI→사람 에스컬레이션 통로")은 가설이다. 이 문서는 PLAN.md 91.1의 산출물로, **결과를 보기 전에** 무엇을 어떻게 재고 어떤 값이면 어떤 결정을 내릴지를 못박는다. 임계치를 데이터를 본 뒤에 정하면 실험이 가설을 확인하는 장치로 변질되기 때문이다.

> **상태: 설계 확정, 결과 수집 전.** 이 문서가 커밋된 시점의 git 해시를 사전 등록(pre-registration)으로 삼는다. 이후 임계치나 과제 목록을 바꾸려면 변경 이유를 아래 "변경 이력"에 남긴다.

## 1. 무엇을 검증하는가

ADR-0069가 의존하는 주장을 검증 가능한 가설로 나눈다.

| 가설 | 주장 | 틀렸을 때 의미 |
|---|---|---|
| **H1 채널** | 코딩 에이전트는 MCP로 연결된 Quno를 스스로 조회한다 | 아무리 좋은 기록이 있어도 소비되지 않는다 |
| **H2 커버리지** | 좁은 스택에서 현실적인 규모의 기록으로 의미 있는 비율의 실제 에러에 적중한다 | 콜드 스타트가 풀리지 않는다 |
| **H3 가치** | 적중하면 에이전트가 더 빨리·적은 토큰으로 해결한다 | 기록이 있어도 에이전트 혼자와 차이가 없다 |
| **H4 안전** | 틀린(오래됐거나 악의적인) 기록에 속아 잘못 고치는 비율이 낮다 | 공유 지식이 공급망 공격면이 된다 |
| **H5 에스컬레이션** | 에이전트가 못 푸는 사례가 실제로 존재하고, 사람이 쓸 만한 답을 준다 | AI→사람 통로의 수요가 없다 |
| **H6 메인테이너** | 메인테이너가 실패 시그니처 집계에 구체적 가치를 느낀다 | 벤더·메인테이너 수익 경로(98)가 없다 |

H1~H4는 한 실험(2~4절)으로, H5는 5절, H6은 6절로 잰다.

## 2. 실험 설계 (H1~H4)

### 2.1 대상과 고정 사항

- **스택**: Kotlin + Spring Boot(+Gradle). ADR-0067이 정한 좁은 콜드 스타트 스택이다.
- **에이전트**: 실험 시작 시점에 가장 널리 쓰는 코딩 에이전트 1종. 모델 ID, 에이전트 버전, MCP 서버 커밋 해시를 모든 실행 기록에 남긴다. 실험 도중 업데이트하지 않는다. 가능하면 2종째로 재현해 한 벤더에 대한 과적합을 확인한다.
- **언어**: 질문·기록은 영어 에러 메시지 중심(실제 스택트레이스가 영어이므로).

### 2.2 과제 세트 (30개)

과제 = "특정 프로젝트 상태에서 특정 실패가 나는 재현 저장소 + 성공 판정 명령(테스트 통과 또는 에러 소멸)". 과제를 **시드 기록을 만들기 전에** 확정해 커밋한다.

| 층 | 개수 | 출처 | 보려는 것 |
|---|---|---|---|
| A 최신 | 10 | 최근 90일 내 릴리스에서 생긴 깨짐(Spring Boot 4.x·Jackson 3·Kotlin 2.x 등 마이그레이션 이슈, 릴리스 노트·이슈 트래커에서 선정) | **최신성** — 에이전트 학습 시점 이후 지식. 가설의 핵심 근거 |
| B 롱테일 | 10 | 환경·설정 의존적이고 검색해도 답이 흩어진 에러(컨테이너·인코딩·프록시·의존성 해석 충돌 등) | 환경 단서가 있어야 풀리는 문제 |
| C 통제군 | 10 | 흔하고 문서가 풍부한 에러(NPE, 빈 순환 참조, 일반 설정 오류) | **"대부분 에이전트가 혼자 푼다"는 사고실험의 검증**. 여기서 Quno가 이득을 못 내는 것이 정상이다 |

- 과제는 A·B를 우선하되 C를 반드시 넣는다. C에서 차이가 없다는 것을 확인해야 "수요가 남는 영역"이 A·B에 있다는 주장이 성립한다.
- 이 저장소 자체의 사례([technical-deep-dives.md](../engineering/technical-deep-dives.md), Spring Boot 4 마이그레이션 중 겪은 문제)는 후보가 될 수 있지만, 같은 출처로 시드를 만들면 유출이 되므로 **과제로 쓰면 시드 후보에서 제외**한다(역도 같다).

- **R/L 분리**: 재현 가능한 과제(R/D)와 로그 재생형(L, B층 4개)은 성공 판정의 엄밀성이 달라 **따로 집계**한다. 3.1의 해결률·시간 지표는 R/D 과제로만 계산하고, L은 채점 점수(0~4)로 별도 보고한다. 과제 구성은 [phase-91-task-candidates.md](phase-91-task-candidates.md)와 [experiments/phase-91-tasks](../../experiments/phase-91-tasks/README.md) 참고.

### 2.3 비교군 (과제당 4개 조건)

| 조건 | MCP 코퍼스 | 목적 |
|---|---|---|
| **A0 기준** | 없음 | 에이전트 혼자 |
| **A1 현실** | 시드 약 100건(과제 정답과 독립적으로 수집) | H1·H2·H3 — 실제로 얻을 수 있는 효과 |
| **A2 상한** | A1 + 해당 과제의 정답 기록을 손으로 작성해 추가 | **기록이 완벽하다면 얼마나 가치가 있는가.** 커버리지 문제와 가치 문제를 분리한다 |
| **A3 미끼** | A1 + 과제마다 그럴듯하지만 틀린 기록 1건(오래된 버전의 해법, 증상만 같은 다른 원인) | H4 — 속는 비율. 일부 미끼에는 `unverified` 라벨을, 일부에는 라벨 없음으로 변주해 라벨의 방어 효과도 본다 |

- 실행은 과제 × 조건 × **3회 반복**(에이전트 비결정성) = 30 × 4 × 3 = **360회**. 비용 상한을 넘으면 A·B 층 20개 위주로 줄이고, 줄인 내용을 변경 이력에 남긴다.
- 실행 순서는 무작위화하고, 같은 세션을 이어 쓰지 않는다(컨텍스트 오염 방지). 에이전트에게 주는 첫 프롬프트는 모든 조건에서 동일하다. **조건 간 차이는 MCP 서버 연결 여부와 코퍼스뿐이다.**
- **도구 사용을 유도하는 문구를 프롬프트에 넣지 않는다.** H1(스스로 조회하는가)을 재야 하기 때문이다. 도구 설명(description)은 실제 배포될 문구 그대로 쓴다. 호출률이 낮으면 설명·배치를 고쳐 **한 번만** 재실행한다(변경 이력에 남김).

### 2.4 측정 지표

| 지표 | 정의 | 사용 |
|---|---|---|
| **호출률** | A1에서 에이전트가 첫 해결 시도 전·중 Quno 도구를 1회 이상 호출한 실행의 비율 | H1 |
| **적중률(top-3, 등급)** | 호출한 실행 중 상위 3건의 최고 관련도. **2 = 같은 근본 원인**, **1 = 같은 실패 계열의 실행 가능한 단서**(예: Boot 4 모듈화로 선택 모듈이 빠져 클래스를 못 찾음), 0 = 무관. **적중률 = 관련도 ≥ 1인 비율**, 정확 적중률 = 관련도 2인 비율. 판정은 어느 조건인지 가린 평가자가 한다 | H2 |
| **해결률** | 시간·토큰 상한 안에 성공 판정 명령을 통과한 비율 | H3 |
| **해결 시간·토큰** | 첫 프롬프트부터 성공 판정까지의 벽시계 시간과 총 토큰. 상한까지 못 풀면 상한값으로 처리(중도절단) | H3 |
| **수락률** | 적중한 실행에서 에이전트가 기록의 수정을 실제로 적용한 비율 | H3 |
| **오염률** | A3에서 미끼 수정을 적용했고 그 결과 해결에 실패하거나 다른 부작용이 생긴 비율 | H4 |
| **코퍼스 중복률(leave-one-out)** | 코퍼스의 각 기록을 나머지 기록에 조회했을 때 **같은 근본 원인**의 다른 기록이 있는 비율과 rule-of-three 95% 상한. 코퍼스를 25·50·100건으로 부분 표집해 규모별로 본다 → 정확 적중에 필요한 기록 수의 하한 추정 | H2 |

- 상한: 과제당 20분 또는 정해 둔 토큰 예산.
- **통계 처리**: 30과제 × 3회는 작은 표본이므로 유의성 검정을 주장하지 않는다. 과제 단위 쌍체 비교, 중앙값, 부트스트랩 신뢰구간을 보고하고 층(A·B·C)별로 나눠 본다. "차이가 있어 보인다"가 아니라 "신뢰구간이 임계 아래로 내려가지 않는다"를 기준으로 삼는다.

## 3. 판정 규칙 (사전 등록)

기준 지표는 **A·B층 합산(20과제)**이다. C층은 해석용이다.

### 3.1 Go — 포지셔닝 유지, 92·93·94 착수

다음을 **모두** 만족한다.

1. 호출률 ≥ **60%** (A1, A·B층)
2. 적중률(관련도 ≥ 1) ≥ **30%** (A1 top-3, A·B층 중 R/D 과제, 시드 100건 기준). 정확 적중률과 코퍼스 중복률 상한은 **보고만 하고 Go 조건이 아니다**(2026-10-20 변경, 아래 변경 이력)
3. 적중한 과제의 해결 시간 중앙값이 A0 대비 ≥ **30% 단축**되고 토큰도 감소 (A1 vs A0)
4. 오염률 ≤ **10%** (A3, 라벨 있는 미끼 기준)

그리고 상한 조건 A2가 시간 ≥ 40% 단축을 보여야 한다. A2가 이 값에 못 미치면 위 1~4를 만족해도 "기록이 완벽해도 가치가 작다"는 뜻이라 Go로 보지 않고 3.3으로 간다.

### 3.2 Narrow — 범위를 줄여 한 번 더

A2의 가치는 충분(≥ 40% 단축)하지만 1·2 중 하나가 미달이다. 채널 또는 커버리지 문제이지 가치 문제가 아니다.

- 호출률 미달 → 도구 설명·응답 형식·시작 시 컨텍스트 주입 방식을 고쳐 **한 번** 재실험.
- 적중률 미달 → 코퍼스 중복률 상한으로 필요 규모의 하한을 추정한다. 필요 규모가 현실적이면(약 500건 이하) 시드 확장 후 재측정, 그렇지 않으면 **팀 비공개 기억(Phase 97) 우선**으로 순서를 바꾼다. 자기 팀 기록은 적중률이 구조적으로 높다.
- 오염률 미달 → 96(신뢰·보안)을 92보다 앞당긴다.

### 3.3 Pivot — ADR-0069를 재검토하는 ADR 작성

다음 중 하나다.

- A2의 해결 시간 단축 < **15%** — 완벽한 기록이 있어도 에이전트에게 도움이 안 된다.
- A0만으로 A·B층 해결률 ≥ **90%** (상한 시간 안에) — 에이전트가 최신·롱테일도 혼자 푼다.
- Narrow의 재실험 후에도 같은 항목이 미달.

Pivot 시 후보: (a) 팀 비공개 기억 중심으로 축소(97), (b) 메인테이너·벤더 실패 인텔리전스 중심(98), (c) 사람 중심 Q&A 강화(74~77 되살림). 어느 쪽인지는 5·6절의 결과(H5, H6)로 고른다.

### 3.4 임계치의 근거와 한계

- 30%·60%·30%·10%는 **계산이 아니라 판단**이다. 근거는 "이보다 낮으면 개발자가 도구를 신뢰해 쓸 이유가 약하다"는 정도다. 그래서 사전 등록하고, 틀리면 틀렸다고 기록한다.
- **적중률은 과제와 시드의 겹침을 내가 설계하는 한 편향된다.** 시드는 과제와 독립적인 공개 출처(릴리스 노트, 이슈 트래커, 공개 Q&A)에서 만들고, 과제 정답 문서를 보고 만들지 않는다. 그럼에도 이 값은 "실제 사용 분포에서의 커버리지"의 증거가 아니라 **최소한의 가능성 확인**이다. 실제 커버리지는 코퍼스 중복률과 이후 파일럿(실사용 조회 로그)에서 본다.
- **기준 2의 변경과 한계(2026-10-20, 데이터 수집 전)**: 원래 기준은 "같은 근본 원인 적중률 ≥ 30%"였으나, 시드 105건을 과제와 독립적으로 만든 뒤 확인하니 과제 30개 중 같은 원인의 시드가 0건이고 코퍼스 내부 중복도 0/105(95% 상한 약 2.9%)였다. 이 규모에서는 정확 적중이 구조적으로 0에 가까워 기준이 "가설이 맞는가"가 아니라 "코퍼스가 충분히 큰가"만 재게 된다. 그래서 관련도를 등급화(같은 원인=2, 같은 실패 계열의 단서=1)하고 기준 2를 관련도 ≥ 1로 바꿨다. **이 변경은 코퍼스의 구성(실패 계열이 반복됨)을 본 뒤에 이루어졌다**는 점에서 순수한 사전 등록이 아니다. 에이전트 실행 전에 확정했고 위험은 임계치 30%를 코퍼스를 보고 정하지 않은 것(원래 값 유지)으로 한정했지만, 결과 해석 시 이 사실을 함께 밝힌다.
- 한 사람이 과제 선정·시드 작성·판정을 모두 하면 편향이 크다. 최소한 **적중 판정은 가린 상태에서** 하고, 가능하면 판정자를 설계자와 분리한다([사람] 항목).

## 4. 프로토타입 범위 (91.2)

실험에 필요한 최소만 만든다. 이 단계의 코드는 버릴 수 있다.

- **에러 시그니처 최소판**: Phase 64의 일부. 예외 클래스 + 상위 N개 프레임 정규화. 라인 번호·메모리 주소·타임스탬프 제거.
- **읽기 전용 MCP 서버**: 도구 2개 — `search_known_issues(error_text, stack?)`, `get_resolution(id)`. 응답은 구조화 필드만(ADR-0069 결정 3): 시그니처, 증상, 원인, 수정 요약, 적용 버전 범위, 출처 링크, 검증 상태(`unverified`), 마지막 확인일. 자유 텍스트는 별도 필드에 분리하고 비신뢰로 표시.
- **시드 약 100건**: 아래 주의 참고.
- 인증·저장소는 단순하게(파일 또는 기존 DB의 임시 테이블). 프로덕션 모델은 Phase 92에서 설계한다.

**시드 출처에 대한 정정.** PLAN.md 초안은 "기존 질문·Cluster를 해결 기록 형태로 변환"이라고 적었지만, 이 저장소에는 시드/데모 데이터가 없고 운영 데이터도 없다. 따라서 시드는 **공개 출처에서 새로 큐레이션**해야 한다.

- 허용 출처: 프로젝트 릴리스 노트·마이그레이션 가이드, 공식 이슈 트래커의 닫힌 이슈, 공개 Q&A. 각 기록에 원 출처 링크를 필수로 남긴다.
- 원문을 그대로 복제하지 않고 **구조화 필드로 요약**하며 출처를 표기한다. 라이선스(예: CC BY-SA 출처의 attribution·share-alike)는 실험 단계라도 확인한다 — 공개 서비스에 쓰기 전에는 [사람]이 법무 검토를 한다.
- 시드의 약 절반은 A·B층과 같은 영역(최신·롱테일)에서, 나머지는 인접 영역과 C층 유사 에러에서 모아 "정답이 없는 조회"도 현실적으로 일어나게 한다.

## 5. 에스컬레이션 수요 (H5, 91.4)

- **수집**: A0의 상한 내 미해결 과제, 그리고 실험 참가자(본인 포함)가 최근 에이전트와 작업하다 막힌 실제 사례를 합쳐 **20건**을 모은다. 층별 미해결 비율 자체가 H5의 첫 지표다.
- **지표**
  - 막힘 비율: A·B층에서 A0가 상한 내 해결하지 못한 과제 비율. **5% 미만이면 에스컬레이션 수요가 작다**고 보고 Phase 95의 규모를 줄인다.
  - 응답률·속도: 초대한 개발자 풀(최소 10명)에게 20건을 내보냈을 때 **24시간 내 사용 가능한 답변을 받은 비율 ≥ 50%**.
  - 품질: 질문한 쪽이 "적용해 해결됨"으로 평가한 비율 ≥ **50%**.
- **한계**: 풀이 지인 중심이면 응답률이 부풀려진다. 결과 보고에 풀의 구성을 명시한다. 이 지표가 통과해도 "공개 서비스에서 응답자가 모인다"의 증거는 아니다.

## 6. 메인테이너 인터뷰 (H6, 91.5) — [사람]

- 대상: 사용자 수가 있는 JVM/Spring 생태계 오픈소스 메인테이너 3~5명.
- 유도 질문을 피한다. 먼저 현재의 고통을 묻는다: "릴리스 후 깨졌다는 보고를 어떻게 알아채는가", "같은 문제 보고가 몇 번이나 중복되는가", "지금 쓰는 도구는 무엇이고 무엇이 부족한가". 그 뒤에 환경별로 집계된 실패 시그니처 화면을 보여주고 반응을 본다.
- **기준**: 5명 중 **3명 이상**이 (a) 구체적이고 현재 진행 중인 고통을 말하고 (b) 이 대시보드를 시험 사용하겠다고 약속(이메일 연결, 데이터 접근 허용 등)한다. "좋은 아이디어네요"는 신호로 치지 않는다. 미달이면 Phase 98은 후순위로 내린다.

## 7. 일정·비용·산출물

- **기간**: 2주 타임박스를 권장(과제 선정·시드 큐레이션 3일, 프로토타입 2일, 실행 3일, 분석·보고 2일 + 인터뷰·에스컬레이션은 병행). 이는 추정이며 시드 큐레이션이 가장 큰 변동 요인이다.
- **비용**: 360회 실행의 토큰 비용이 지배적이다. 시작 전에 파일럿 5회로 회당 비용을 재서 상한을 정한다.
- **산출물**: ① 원시 실행 로그(조건·모델·버전 포함)와 집계 표, ② 층별 결과, ③ 3.1~3.3 중 어느 판정인지, ④ 결정 ADR(Go면 ADR-0069 상태를 "승인됨"으로, Narrow/Pivot이면 재검토 ADR).

## 8. 사전에 인정하는 한계

- 시나리오 기반 실험이라 **실제 사용 분포**가 아니다. 호출률은 에이전트가 새 버전이 나올 때마다 달라질 수 있다.
- 에이전트 벤더가 같은 기능을 직접 만들 위험([competitive-analysis.md 7.8](competitive-analysis.md))은 이 실험으로 검증할 수 없다. 별도로 계속 감시한다.
- A·B층 과제 선정이 "Quno에게 유리한 사례"로 기울 수 있다. 선정 기준(최근 90일, 환경 의존성)과 출처를 과제마다 기록해 외부 검토가 가능하게 한다.
