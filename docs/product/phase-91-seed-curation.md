# Phase 91 — 시드 코퍼스 큐레이션 기록

[실험 설계](phase-91-validation-experiment.md) 4절의 "시드 약 100건"을 만든 과정과 한계다. 결과물은 [experiments/phase-91-mcp/seeds](../../experiments/phase-91-mcp/seeds/README.md)의 105건이다.

## 1. 절차

1. **후보 수집**: 공개 GitHub 저장소 32곳(Spring Boot·Framework·Security·Data·Batch·Kafka, Gradle, Jackson, Testcontainers, Micrometer, springdoc, Lombok, Reactor Netty, Liquibase, Lettuce, Ktor 등)에서 2025-06-01 이후 생성된 닫힌 이슈 중 본문에 예외가 있는 것 248건을 모았다. 과제 30개와 원인이 겹치는 주제(Docker 29 최소 API, DevTools·JDBC 모듈, 빈 issuer 등 20여 개)와 과제 이슈 번호 자체를 제외하고, 백포트 중복을 합쳐 저장소당 최대 18건으로 206건을 남겼다.
2. **큐레이션**: 4개 에이전트가 각 약 52건의 이슈와 댓글을 읽고, **원인과 해결(수정 버전·설정·우회)이 스레드에서 확인되는 것만** 기록했다. `errorSample`은 이슈 원문에서 그대로 인용하고(경로·사용자명 정제), 증상·원인·해결 요약은 영어로 직접 썼다. 추론은 `notes`에 표시했다.
3. **수율**: 206건 중 105건(51%). 제외 사유는 해결 미기재(가장 많음), 원인 불명·논쟁, 수정 버전을 알 수 없는 업그레이드뿐인 해결, 예외 없는 동작 버그, 너무 좁은 사례, AI 생성 보고서(원인 분석 없음)였다.

## 2. 품질 검증

| 검사 | 결과 |
|---|---|
| 스키마 검증(`validate-seeds`) | 105건 통과, 0건 거부 |
| 중복 id | 없음 |
| 자유 텍스트의 AI 대상 지시문·URL·명령어 패턴 | 없음 |
| `errorSample` 원문 일치(이슈·댓글에 줄 단위로 존재하는가) | 전수 확인. 불일치는 정제(패키지명을 `com.example`로 치환) 3건뿐. 첫 실행의 14건 플래그는 GitHub API 속도 제한으로 빈 응답을 받은 검사 오류였고, 재시도로 해소 |
| 수정 버전 vs 이슈 마일스톤 | 마일스톤이 본문에 없는 10건에 마일스톤을 `notes`에 사실로 추가(백포트 여부는 불명시) |
| 과제 키워드 스캔(30개 과제의 정답 용어) | 일치 0건 |
| 과제 실패 출력을 코퍼스에 조회 | **같은 근본 원인의 기록 0건.** 유사한 예외 클래스의 오답 후보가 일부 나옴(A05↔HQL 주석 이슈, A10↔SAML2 스타터 이슈). 이는 현실적인 방해 요소다 |

검증 중 MCP 프로토타입의 파서도 고쳤다: ① 따옴표 문자열을 모두 지우던 정규화가 JDK의 "helpful NPE" 메시지(코드 이름이 들어 있음)를 구분 불가능하게 만들었다 → 이 형태는 따옴표 안을 보존. ② `org/springframework/...` 같은 JVM 내부 클래스 이름이 경로로 지워졌다 → 파일 경로만 정규화. ③ 전체 Gradle 로그를 넣으면 태스크 이름 `checkKotlin...Error`를 예외로 잡았다 → 클래스 이름은 대문자로 시작해야 한다.

## 3. 구성

105건: Spring Framework 15, Spring Batch 13, Jackson 12, Gradle 12, Spring Data JPA 11, Spring Boot 8, springdoc 5, Spring Data Commons 4, 그 외(Security, Kafka, Mongo, Lettuce, Lombok, Reactor Netty, Micrometer, Testcontainers, Ktor, Liquibase, AMQP, Cloud Gateway, H2) 나머지. 보고 시기는 2025-06 이후다.

## 4. 한계 — 실험 해석에 중요한 것

1. **선택 편향**: 예외가 있고 원인·해결이 확인되는 이슈만 들어 있다. "원인 불명"이나 "재현 안 됨"은 걸러졌으므로 실제 이슈 스트림보다 깨끗하다.
2. **A1 조건의 적중률은 구조적으로 0에 가깝다.** 시드를 과제와 독립적으로 만들었으므로(유출 방지) 30개 과제 중 같은 원인의 시드는 없다. 코퍼스 내부에서도 한 기록이 다른 기록과 같은 문제인 경우는 **105건 중 0건**이었다(강한 매치 4건은 모두 서로 다른 원인의 일반적인 메시지 일치: NPE·OOM·`object is not an instance of declaring class`). 즉 "서로 다른 이슈가 같은 에러를 반복한다"는 비율이 100건 규모에서는 측정되지 않는다. 이 때문에 실험 설계 3.1의 기준 2(적중률 ≥ 30%)는 A1에서 달성될 수 없고, **A1은 호출률(H1)·오염률(H4)·방해 요소에 대한 반응을 재는 용도로만 의미가 있다.** 코퍼스 성장 곡선도 적중이 0이면 외삽할 수 없다. → 설계 보완 필요(아래 5절).
3. **라이선스**: 이슈 본문은 작성자 저작물이다. 기록은 사실 요약이고 원문은 짧은 에러 인용만 담았지만, 공개 서비스에 쓰기 전에 [사람]이 법무 검토를 해야 한다(실험 설계 4절).
4. **영어 요약**: 에이전트 소비를 가정해 영어로 썼다. 사람이 읽는 화면용 번역은 하지 않았다.
5. **큐레이터가 에이전트**다. 요약의 정확성은 위 검증(원문 일치, 마일스톤 대조)으로 부분적으로만 보증된다. 의미 수준의 오류(원인 요약이 틀림)는 표본 검토가 필요하다.

## 5. 설계 보완 제안 (결정 필요)

실험 설계는 "A1 적중률 ≥ 30%"를 Go 조건으로 사전 등록했지만, 위 2번 때문에 현재 코퍼스로는 달성 불가능하다. 임계치를 결과 이후에 바꾸지 않는다는 원칙에 따라, **데이터 수집 전에** 다음 중 하나를 정해 설계 문서의 변경 이력에 남겨야 한다.

- **(권장) 적중률을 두 개로 나눈다.** ① *커버리지 적중률*: 코퍼스가 과제와 같은 종류의 문제(최근 Boot 4/Framework 7 회귀)를 실제로 다루는 현실적 상황을 모사하도록, 과제와 **같은 모듈·시기의 다른 이슈**를 더한 코퍼스(A1')로 측정. ② *상한 적중률*: A2(정답 기록 추가)는 그대로. 3.1의 기준 2는 A1'에 적용.
- 또는 기준 2를 삭제하고 Go 판정을 호출률·상한 가치(A2)·오염률로만 하되, 커버리지는 별도 파일럿(실사용 조회 로그)으로 넘긴다.
- 또는 100건 규모의 한계를 인정하고 코퍼스를 크게 늘린다(수백~수천 건). 큐레이션 비용이 선형으로 늘어 비현실적일 수 있다.
