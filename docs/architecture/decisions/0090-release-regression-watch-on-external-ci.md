# ADR-0090: 신규 릴리스 회귀 감시 — 대기열 없이 계획 API가 최신 릴리스를 돌리고, 직전 버전과 달라졌을 때만 알리며, 상태는 사람이 바꾼다

- 날짜: 2026-11-05
- 상태: 승인됨

## 배경 (Context)

PLAN.md Phase 82는 새 릴리스가 나오면 검증된 답변을 다시 실행하고, 깨졌으면 "깨짐 감지" 증거와 재검토 알림을 보내라고 한다. 선행인 81은 외부 CI 기반으로 진행했다(ADR-0088).

쓸 수 있는 재료는 다음과 같다.

- 일 1회 릴리스 스캔과 태그별 최신 버전(`technology_releases`, ADR-0033)
- 태그와 패키지의 큐레이션 매핑(`TrackedTechnologies.PACKAGES`, ADR-0077)
- 워크플로가 실행 전에 묻는 계획 API(ADR-0088)

ADR-0033의 원칙 "감지는 알림까지만, `OUTDATED` 자동 전환은 없다"는 그대로 유지한다. PLAN 82.2도 같다.

## 결정 (Decision)

### 1. 대기열 대신 계획 API가 릴리스를 본다

- 릴리스가 감지됐을 때 캡슐마다 쓰는 일(fan-out)은 없다. 스캔이 `technology_releases`를 갱신하면, 다음 계획 호출이 이를 읽는다.
- 캡슐의 매트릭스 패키지가 추적 기술의 패키지이면(`tagForPackage`), 그 최신 릴리스가 **항상 매트릭스의 한 칸**이 된다. 5칸 상한에서도 이 칸을 먼저 확보한다.
- 그 릴리스의 실행이 아직 없으면 계획은 조회 간격과 상관없이 `new-release`로 바로 실행하라고 답한다.
- **예산은 ADR-0088의 틀 안에 있다.** 칸은 5개까지고, 릴리스당 재실행은 사실상 한 번이다. 비용은 저장소 주인의 CI 분이다.
- 추적 기술이 아닌 패키지는 릴리스를 알 수 없으므로 대상이 아니다(패키지별 릴리스 목록은 Phase 83에서 정한다).
- PLAN은 "검증된 답변"을 대상으로 적었지만, 답변 검증은 아직 정의만 있다(ADR-0089). 그래서 대상은 질문의 재현 캡슐이다.

### 2. 판정은 직전 버전과의 비교

캡슐의 실행 결과는 "버그가 보이는가"다. 그래서 다음처럼 읽는다.

- **BROKE(깨짐 감지):** 직전 버전은 재현 안 됨, 새 릴리스는 재현됨
- **FIXED(수정 후보):** 직전 버전은 재현됨, 새 릴리스는 재현 안 됨

오탐을 줄이는 조건은 다음과 같다.

- 양쪽 모두 Quno 워크플로·호스티드 러너의 **판정이 난** 실행이어야 한다. 빌드 실패나 직접 작성한 워크플로는 릴리스에 대해 아무것도 말하지 않는다.
- **같은 환경**끼리만 비교한다. OS나 JDK 차이를 릴리스 탓으로 돌리지 않는다.
- **최신 릴리스 칸에서만, 칸마다 처음 한 번만** 판정한다. 캡슐을 처음 붙여 옛 버전들을 차례로 돌릴 때 경계 버전마다 깨짐처럼 보이는 일을 막는다.
- 결과가 뒤바뀐 원인이 flaky일 수 있으므로 "깨졌다"고 단정하지 않고 증거로 보여 준다.
- BROKE는 에러 시그니처 일치를 요구하지 않는다. 다른 에러여도 직전 버전에서 통과하던 것이 실패했으면 읽어 볼 가치가 있다. 어떤 에러인지는 로그 비교에서 보인다.

### 3. 알림과 상태

- `RELEASE_REPRODUCTION_CHANGED` 이벤트를 질문 작성자, Ward 구독자, 답변 작성자에게 보낸다. 비공개 질문은 발송 시 멤버십을 확인한다(ADR-0085).
- 질문 상태는 바꾸지 않는다(ADR-0033). 등급은 기존 규칙대로 칸별 최신 실행으로 판정한다(ADR-0089).

### 4. 증거 표시

- 재현 패널에 `깨짐 감지 · 3.7.0 → 3.8.0`과 환경, 시각을 표시한다.
- **로그 비교:** `GET /questions/{id}/reproduction/runs/{runId}/compare`가 두 실행의 로그를 줄 단위로 비교해 돌려준다(기존 `TextDiffer`). 가린 뒤의 로그만 쓴다.
- **로그 보관:** 전환 실행과 비교 대상 실행의 로그는 최신 20건 규칙에서 뺀다. 증거가 먼저 사라지면 안 된다. 그래도 로그가 없으면 `logsAvailable: false`로 답한다.
- Evidence Card에 `releaseTransitions`를 더한다.

## 결과 (Consequences)

- 릴리스 스캔은 바뀌지 않는다. 새 쓰기 경로 없이 하루 안에 캡슐들이 새 릴리스를 돌린다. 실제 시점은 저장소 cron에 달렸다.
- 저장소 빌드가 `qunoVersion`을 받아야 동작한다. 새 메이저로 빌드가 깨지면 `BUILD_FAILED`로 남고 깨짐 감지는 나오지 않는다. 이 경우 빌드 실패와 버그를 구분할 수 없기 때문이다.
- 최신 릴리스 하나만 본다. 스캔 간격 안에 두 릴리스가 나오면 앞의 것은 건너뛴다(스캔이 최신 하나만 저장한다).
- 검증
  - `ReproductionPlanTest`: 릴리스 칸 확보, `new-release`, BROKE·FIXED, 비교 제외 조건
  - `ReproductionRunE2ETest`: 릴리스 → 계획 → 기준선 → BROKE 한 번 → 로그 비교 → 세 수신자 알림 → 상태 불변 → 다음 릴리스 FIXED → 카드
  - 브라우저: 패널 표시와 로그 비교
