# ADR-0070: 질문은 증거 자료다 — 환경 스냅샷 자동 수집과 검증된 질문 등급

- 날짜: 2026-10-19
- 상태: 승인됨

## 배경 (Context)

[ADR-0069](0069-agent-era-positioning-verified-fix-memory.md)가 Quno의 주 소비자를 AI 에이전트로 정했다. 에이전트는 "그럴듯한 글"이 아니라 **인용할 수 있는 근거**가 필요하다. 지금 질문은 두 가지가 약하다.

- **환경 정보가 사람 손에 달려 있다.** `environment`는 자유 텍스트이고, 사람은 가장 중요한 단서(로케일·인코딩, 컨테이너 여부, 해석된 의존성 버전, 마지막으로 잘 되던 때와의 차이)를 빠뜨린다. 그래서 재현이 안 되고 답이 어긋난다.
- **질문의 품질을 검증하는 절차가 없다.** 답변은 투표와 채택이 있지만 질문이 "실제로 존재하는 실패인가"를 확인하는 기준이 없어, 질문이 근거 자료로 쓰일 수 없다.

사용자가 두 방향을 제안했다. (1) 에이전트가 APM 에이전트가 메트릭을 수집하듯 그 순간의 컴퓨터 상태를 가능한 한 구체적으로 자동 첨부한다. (2) 특정 절차와 조건으로 검증된 질문을 만들어, AI가 참고할 정확한 근거 자료로 쓰이게 한다.

## 결정 (Decision)

### A. 환경 스냅샷

1. **상시 모니터링이 아니라 이벤트 기반 캡처다.** 질문·해결 기록 제출, 에스컬레이션, 실패 시점에만 수집한다. 에이전트는 최근 명령·출력의 **링 버퍼를 로컬 메모리에만** 유지하고, 실패 때 동결해 첨부한다(블랙박스 기록기). 서버로 상시 전송하지 않는다.
2. **수집·정제·미리보기·동의는 모두 로컬에서 끝낸다.** 서버에 닿기 전에 비밀값 스캔(패턴 + 엔트로피), 경로·사용자명·호스트·IP 정규화, 필드별 포함/제외 미리보기를 거친다. 동의는 건별이며 철회(삭제)할 수 있다.
3. **민감도를 3계층으로 나눈다.**
   - **Tier 0 (기본)**: OS·아키텍처·커널, 런타임(JDK 벤더+버전, Node 등), 컨테이너/가상화 여부(Docker, WSL, Rosetta), 로케일·인코딩·타임존, 도구 버전(Gradle/Maven/npm), IDE, **해석된 의존성**(선언이 아니라 resolved), 정제된 JVM 인자, CI 여부, git 커밋 SHA와 dirty 여부(원격은 호스트만).
   - **Tier 1 (진단)**: 실패 직전 로그 창, 실행한 명령과 종료 코드, 허용목록 환경변수, 설정 파일의 키(값은 정제), 실패한 테스트 출력.
   - **Tier 2 (런타임 관측, 옵트인)**: 메모리·디스크·cgroup 한도, 의존 서비스 버전(DB·Redis 연결 메타데이터), 스레드 덤프(행·타임아웃 시), OOM 이벤트, 열린 연결 수.
   - **절대 수집하지 않음**: 자격 증명·토큰·개인 키, 허용목록 밖 환경변수 값, 선택하지 않은 소스 파일 내용, 브라우저 기록, 사용자·호스트 식별자.
   - 공개 질문의 기본은 Tier 0+1, Tier 2는 옵트인, 비공개(조직) 질문은 조직 정책을 따른다.
4. **증상 기반 수집 프로파일.** 모든 것을 모으지 않고 에러 종류에 맞는 항목만 더한다(예: OOM → 힙·cgroup, DB 타임아웃 → 커넥션 풀·DB 버전, 의존성 해석 실패 → 레지스트리·프록시 설정). 최소 수집 원칙이고 질문이 잡음으로 덮이는 것도 막는다.
5. **기준선 대비 델타를 가장 높게 친다.** "마지막으로 잘 되던 때(마지막 성공 빌드·CI) 이후 무엇이 바뀌었나" — 의존성 변경, 커밋 요약(파일명만), 설정 변경 — 를 함께 첨부하고 환경 차이를 diff로 보여준다.
6. **환경 지문(콘텐츠 주소 해시).** 정규화한 환경 튜플의 해시로 같은 환경끼리 묶고 중복을 제거한다. 영향 매트릭스(Phase 72), 깨짐 레이더(Phase 69), 러너의 환경 이미지 레시피 생성(Phase 81)이 이 해시를 쓴다.
7. **수집기 서명과 신뢰 표시.** 공식 수집기가 만든 스냅샷은 서명된다. 수동 입력은 허용하되 "수동 입력"으로 낮은 신뢰를 표시한다.

### B. 검증된 질문

1. **질문도 증거 자료다.** 검증된 질문은 "이 환경에서 이 실패가 실제로 발생한다"는 증거 자료다. 에이전트에게는 자유 글이 아니라 **Evidence Card**(주장, 검증 등급, 마지막 재현 시각, 실행 로그 링크, 환경 지문, 에러 시그니처, 업스트림 링크, 주의 사항)라는 구조화 객체로 준다.
2. **검증 등급과 조건은 공개한다.**

| 등급 | 이름 | 조건 |
|---|---|---|
| L0 | 미검증 | 자유 텍스트 초안 |
| L1 | 구조 충족 | 필수 항목(에러 시그니처, 환경 스냅샷, 기대/실제 동작, 재현 절차)이 있고 비밀 스캔·린트·중복 검사를 통과 |
| L2 | 재현됨 | 최소 재현 코드를 러너가 선언한 환경에서 실행해 실패를 재현했고, **재현 결과의 에러 시그니처가 보고된 시그니처와 일치** |
| L3 | 독립 확인 | 서로 다른 환경 지문을 가진 독립된 N명(또는 에이전트)이 재현을 확인했거나 메인테이너가 확인 |
| L4 | 원인 규명 | 업스트림 이슈/커밋에 연결되고 영향 버전 범위가 이분 탐색(Phase 83) 등으로 확정되어, 수정 릴리스 여부까지 기록 |

   사용자는 등급을 올리는 방법("최소 재현 코드를 추가하면 L2")을 화면에서 안내받는다.
3. **"같은 실패인가"가 핵심 검사다.** 재현이 성공했더라도 다른 에러가 났다면 L2가 아니다. 시그니처 일치 여부를 반드시 확인한다.
4. **등급은 시간이 지나면 강등될 수 있다.** 새 릴리스 후 재검증에서 더 이상 재현되지 않으면 "재현 안 됨"(수정되었거나 환경이 달라졌다는 증거)으로 표시하고, 정해진 기간 재검증하지 못하면 "오래됨"으로 표시한다. 이의가 제기되면 재실행한다. 오용·버그 아님으로 판정된 질문도 별도 분류로 보존한다.
5. **검증 파이프라인**: 제출 → 린트·비밀 스캔 → 시그니처 정규화·중복 → 스냅샷 검증(스키마, 수집기 서명, 빌드 파일과의 일관성) → 러너 재현 → 등급 부여 → (L3·L4는) 독립 확인·메인테이너 확인 → 주기적 재검증.
6. **검증 결과가 노출 순서를 정한다.** 검색과 MCP 응답은 등급순으로 정렬한다. 답변의 검증은 이 위에서 정의한다: 검증된 재현 코드에 해결책을 적용했을 때 테스트가 통과해야 한다.

## 결과 (Consequences)

- **수집 정책이 곧 신뢰다.** 과수집은 사용자 신뢰와 법적 위험(개인정보, 기기 식별자)을 한꺼번에 잃는다. 그래서 로컬 정제, 계층화, 최소 수집, 건별 동의, 수집 금지 목록을 설계의 전제로 두고, 정제 누수는 알려진 비밀 패턴 코퍼스로 테스트한다.
- **스키마를 버전 관리해야 한다.** 수집기와 서버가 어긋나도 오래된 스냅샷을 읽을 수 있어야 한다.
- **검증 비용이 든다.** L2 이상은 러너 실행이므로 비용 상한·캐시·우선순위([ADR-0068](0068-living-engine-runner-and-ai-first-responder.md))를 따른다. L1까지는 실행 없이 가능하므로 처음에는 L1을 넓게, L2는 좁게 적용한다.
- **"재현됨"은 정답이 아니라 "이 실패가 존재한다"는 증거**일 뿐이다. flaky하거나 재현 코드가 문제를 잘못 모사할 수 있어 원시 로그를 항상 열람할 수 있게 하고 이의를 받는다.
- 에이전트에 주는 필드는 구조화 데이터만이다. 자유 텍스트는 비신뢰로 분리해 프롬프트 인젝션을 막는다(Phase 96).
- [Phase 63](../../../PLAN.md)의 정적 Stack Fingerprint는 이 스냅샷의 Tier 0 일부가 된다. 구현은 63에서 의존성 모델을 만들고 93에서 런타임·진단 계층과 수집기를 더하는 순서다.
