# ADR-0077: 답변 적용 범위 — 패키지별 `[이상, 미만)` 반열린 구간과 자체 버전 비교기, 범위가 있는 질문만 재검토 알림을 좁힌다

- 날짜: 2026-10-27
- 상태: 승인됨

## 배경 (Context)

[ADR-0076](0076-stack-fingerprint-dependency-parsing.md)로 질문에 `(생태계, 패키지, 버전)`이 붙었다. 하지만 답변이 어느 버전에서 유효한지는 여전히 본문 문장으로만 알 수 있다.

버전 영향 감지([ADR-0033](0033-technology-version-scan-detection-only-no-auto-outdated.md))는 태그와 "콘텐츠가 릴리스보다 오래됨"만 본다. 그래서 새 패치가 나올 때마다 그 태그가 붙은 질문 전부에 재검토 알림이 간다. 답변이 이미 "4.0 미만에서 유효"라고 밝혔다면 3.5 릴리스는 알릴 일이 아니다.

PLAN.md Phase 63.3·63.4가 이 둘을 다룬다.

## 결정 (Decision)

### 범위 표현: 패키지별 `[fromVersion, untilVersion)`

- 답변 하나에 `(생태계, 패키지, fromVersion, untilVersion)` 항목을 최대 20개 둔다.
- `fromVersion`은 **이상**(포함), `untilVersion`은 **미만**(제외)이다. 둘 중 하나는 있어야 하고, 둘 다 있으면 `from < until`이어야 한다.
- **상한을 "미만"으로 둔 이유:** "3.3.5까지 확인함" 같은 포함 상한은 다음 패치가 나오는 순간 범위를 벗어난다. 그러면 63.4의 알림이 지금보다 시끄러워진다. 작성자가 "4.0 미만"처럼 호환이 깨질 지점을 적게 하는 편이 알림을 좁히는 목적에 맞는다.
- npm식 `^3.2.0`·Maven식 `[3.2,4.0)` 문자열은 받지 않는다. 생태계마다 문법이 달라 사용자가 헷갈린다. 화면은 "이상/미만" 두 칸으로 받는다.

### 버전 비교기: 도메인에 직접 구현

- 숫자 부분은 마디별로 비교하고, 빠진 마디는 0으로 본다(`3.2` = `3.2.0`).
- 접미사는 `alpha < beta < milestone(M) < rc(CR) < snapshot < 정식(없음·GA·FINAL·RELEASE) < sp` 순이다. 같은 단계 안에서는 뒤의 숫자로 비교한다(`rc1 < rc2`). 모르는 접미사는 rc와 같은 단계에서 문자열로 비교한다.
- 앞의 `v`와 semver 빌드 메타데이터(`+…`)는 무시한다.
- 사전 릴리스는 정식보다 낮다(Maven·semver와 같음). 그래서 `4.0.0-RC1`은 `[3.2, 4.0)` 안에 든다. 릴리스 피드(endoflife.date)는 정식 릴리스만 알려주므로 알림에는 영향이 없다.
- `3.x` 같은 와일드카드는 버전으로 받지 않는다.
- 질문 지문의 선언 버전(`^3.2.0`, `~1.4`)은 범위 기호를 떼고 하한값으로 읽는다.
- **라이브러리를 쓰지 않은 이유:** Maven `ComparableVersion`은 `maven-artifact` 의존성을 끌고 오고, npm semver는 JVM 구현이 마땅치 않다. 위 규칙이 이 기능이 비교하는 Maven·npm 버전을 충분히 다루고, 경계값을 테스트로 고정할 수 있다.

### 저장

- `answer_applicability_ranges`에 최신 판본만 둔다(ADR-0076과 같은 이유).
- 답변 수정에서 `applicability`를 생략하면 유지하고, 빈 목록을 보내면 지운다.
- 답변이 지워지면 함께 지운다(ON DELETE CASCADE, 파생 색인 테이블과 같은 정책).

### 영향 감지 정밀화(63.4)

`TrackedTechnologies`에 태그별로 해당 제품을 가리키는 패키지 패턴을 둔다. 예: `spring-boot` → `org.springframework.boot` 플러그인, `org.springframework.boot:spring-boot*`.

새 릴리스가 감지되면, 기존 후보(태그 + 오래된 콘텐츠)마다 답변들의 적용 범위 중 이 패키지에 해당하는 것을 본다.

| 상황 | 알림 |
|---|---|
| 해당 범위가 하나도 없음 | 지금처럼 보낸다(`reason: NO_RANGE`) |
| 어느 하나라도 새 버전을 포함 | **보내지 않는다** — 답변이 이미 이 버전도 유효하다고 밝혔다 |
| 모두 새 버전을 벗어남 | 보낸다(`reason: OUT_OF_RANGE`) |

- 새 버전 문자열을 해석하지 못하면 지금처럼 보낸다.
- `GET /qunobot/version-impacts` 목록도 같은 규칙으로 거른다. 알림과 목록이 다르면 혼란스럽다.
- 자동 OUTDATED 전환은 여전히 하지 않는다(ADR-0033 유지).
- **후보 집합은 넓히지 않는다.** 태그 없이 지문에만 패키지가 있는 질문은 이번에 후보로 넣지 않는다. 범위가 없는 답변이 대부분인 지금 후보를 넓히면 알림만 늘어난다. 범위 데이터가 쌓인 뒤 다시 본다.

## 결과 (Consequences)

- 범위를 적은 답변이 많아질수록 재검토 알림이 정확해진다. 적지 않은 질문은 지금과 똑같이 동작하므로 손해는 없다.
- 자체 비교기는 `1.0.0-foo.3` 같은 드문 접미사 조합에서 Maven·npm과 다르게 정렬할 수 있다. 영향은 알림 하나가 더 가거나 덜 가는 정도이고, 경계값 테스트로 주요 경우를 고정했다.
- 제품↔패키지 매핑은 손으로 관리한다. 매핑이 없는 태그(redis, postgresql 등 서버 제품)는 범위가 있어도 `NO_RANGE`로 취급된다.
