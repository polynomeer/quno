# ADR-0091: 버전 이분 탐색 — 작성자가 시작하고, 레지스트리에서 후보를 얼려 두고, 실행 기록을 다시 읽어 경계를 찾되, 경계는 승인 전까지 제안일 뿐이다

- 날짜: 2026-11-05
- 상태: 승인됨

## 배경 (Context)

PLAN.md Phase 83은 어느 버전부터 문제가 생겼는지 자동으로 찾아, 적용 범위와 영향 매트릭스 **제안**으로 열라고 한다. 자동 반영은 하지 않고 작성자가 승인한다. ADR-0070은 L4(원인 규명)의 조건으로 이분 탐색 등으로 확정한 영향 범위를 꼽았다.

매트릭스(ADR-0088)와 회귀 감시(ADR-0090)는 질문이 이미 아는 버전만 돌린다. 그 사이를 찾으려면 패키지별 릴리스 목록이 필요하다. 실행은 계속 저장소의 GitHub Actions에서 한다.

## 결정 (Decision)

### 1. 릴리스 목록은 레지스트리에서 직접 읽는다

- `group:artifact`는 Maven Central의 `maven-metadata.xml`, 그 밖에는 npm 레지스트리에서 읽는다(축약 문서).
  - endoflife.date는 제품 단위라 패키지 버전을 모른다.
  - GitHub Releases는 패키지와 저장소를 잇는 매핑이 또 필요하다.
- Gradle 플러그인 ID는 지금 지원하지 않는다.
- 패키지 이름은 사용자 입력이므로, 형식을 검사한 뒤에만 URL에 넣는다. `..`는 거절하고 호스트는 설정값으로 고정한다. 응답은 8MB, 시간은 5초로 제한한다. XML 파서는 쓰지 않고 `<version>` 태그만 읽는다.
- 읽지 못하면 503으로 답하고 탐색을 시작하지 않는다.
- 호출은 탐색을 시작할 때 **한 번**이고 데이터베이스 트랜잭션 밖에서 한다(ADR-0033과 같은 이유).
- 후보는 그때의 **안정 릴리스**로 얼려 둔다. 이후 새 릴리스가 나와도 탐색 범위는 움직이지 않는다. 사전 릴리스는 사람들이 올리는 대상이 아니므로 뺀다.

### 2. 작성자가 시작한다

- 탐색은 자동으로 시작하지 않는다. 비용은 저장소의 CI 분이고 최대 10회다. 그래서 작성자의 동의를 받는다.
- 화면에서는 깨짐 감지·수정 후보에서 시작한다.
- API는 양 끝을 받으며, 두 끝 모두 신뢰 실행의 판정이 있고 결과가 달라야 한다.
- 캡슐당 하나만 돌고(부분 유니크 색인), 캡슐을 바꾸면 취소된다.

### 3. 탐색은 실행 기록을 다시 읽는 순수 함수다

`VersionBisect.evaluate(후보, 시작 결과, 끝 결과, 관측)`는 저장된 탐색 상태 없이 매번 관측을 다시 읽는다. 늦거나 중복된 보고는 답을 다듬을 뿐, 상태를 망가뜨리지 않는다.

- **큐가 없다.** 워크플로가 묻는 계획 API(ADR-0088)가 탐색 중에는 `reason: bisect`로 다음 버전을 답한다. 조회 간격이나 새 릴리스보다 먼저다. 작성자가 이미 동의했기 때문이다.
- **한 번에 최대 3개 버전:** 범위를 균등하게 나눠 3개를 함께 돌린다. cron은 하루 한 번이므로, 하나씩 돌리면 후보 30개에 5일이 걸린다. 칸마다 작업이 따로 도니 실행 횟수는 조금 늘어도 기다리는 시간이 크게 준다.
- **실행 상한 10회:** 초과하면 `BUDGET_REACHED`로 끝내고 좁혀진 범위를 보여 준다.
- **신뢰 실행만 센다:** Quno 워크플로와 호스티드 러너(ADR-0089).
- **환경 문자열은 비교하지 않는다.** 러너 이미지의 패치 버전이 바뀌면(`java 21.0.5` → `21.0.6`) 탐색이 영원히 끝나지 않기 때문이다. 탐색 시작 뒤 같은 캡슐의 실행을 모두 읽는다.

### 4. 비단조와 flaky

실행 결과가 항상 깨끗한 단조 함수는 아니므로, 단정하지 않고 신뢰도를 함께 낸다.

- 각 버전은 **가장 최근 판정**으로 읽는다.
- 경계를 찾으면 **양쪽을 한 번씩 더** 실행한다. 단일 실행의 flaky가 답을 정하지 못하게 한다.

| 신뢰도 | 조건 |
|---|---|
| 높음 | 양쪽 모두 두 번 실행했고 어긋나는 관측이 없음 |
| 보통 | 일관되지만 상한 때문에 한쪽이 한 번만 실행됨 |
| 낮음 | 어느 버전이 두 결과를 다 냈거나, 경계 위 버전이 경계 아래처럼 행동함 |

- 판정을 내지 못하는 버전(예: 빌드 실패)은 건너뛴다. 사이에 판정 난 버전이 남지 않으면 `UNRESOLVED`와 좁혀진 범위로 끝난다.

### 5. 경계는 제안이다

- 찾은 경계는 `PENDING`이고, 작성자에게 알린다(`VERSION_SEARCH_FINISHED`).
- 작성자가 **승인**해야 Evidence Card의 `versionBoundary`에 들어간다. 거절해도 기록은 남는다.
- 답변의 적용 범위(ADR-0077)는 답변 작성자의 판단이므로 자동으로 고치지 않는다. 영향 매트릭스 표시는 Phase 72가 이 승인된 경계를 읽는다.
- 검증 등급은 바뀌지 않는다. L4는 업스트림 연결(Phase 68)도 필요하다.

## 결과 (Consequences)

- 실제 Maven Central 호출이 Quno의 새 외부 의존이 된다. 탐색 시작 때만 호출하므로 장애가 다른 기능에 번지지 않는다.
- 후보가 많아도 3개씩 나누면 10회 안에 대개 끝난다. 끝나지 않으면 범위를 알려 준다.
- 하루 한 번 cron이면 탐색에 며칠이 걸릴 수 있다. Actions 탭에서 직접 실행하면 앞당길 수 있다.
- 버전 번호 순서와 출시 순서가 다를 수 있다(유지보수 브랜치). 번호 순서로 찾으므로, 3.7.2가 3.8.0보다 늦게 나왔어도 3.7.2를 먼저 둔다.
- 검증
  - `VersionBisectTest`: 경계 찾기, 균등 분할, 인접 끝, 판정 불가 건너뛰기, 비단조, flaky, 상한, 후보 필터
  - `ReproductionRunE2ETest`: 시작 조건, 권한, 중복 시작, 계획과 보고 반복, 사전 릴리스 제외, 승인 전후 카드, 레지스트리 실패 503
  - 브라우저: 실제 Maven Central의 kafka-clients 목록으로 3.6.0~3.9.0을 탐색해 경계 3.8.0을 찾고 승인. 실행 결과는 테스트용 토큰으로 보냈다. 이 과정에서 표의 버전 정렬 문제를 찾아 고쳤다.
