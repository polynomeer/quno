# ADR-0068: 살아있는 엔진 — 격리 러너로 재현을 증명하고, AI는 라벨 붙은 1차 응답자로 참여한다

- 날짜: 2026-10-19
- 상태: 승인됨 (ADR-0067의 결정 2·5를 대체)

## 배경 (Context)

[ADR-0067](0067-differentiation-roadmap-priorities-and-boundaries.md)은 두 가지를 못박았다. 결정 2는 "AI는 답변을 생성하지 않는다", 결정 5는 "서버는 사용자 코드를 임의 실행하지 않는다"였다. 이후 사용자가 더 큰 구상을 제시했다.

- 백엔드에서 엔진이 끊임없이 돌며 질문·답변을 훼손 없이 다듬고, 코드가 있으면 버전별로 실제로 실행해 재현 여부와 **마지막 재현 시각**을 기록한다.
- IDE에서 에러 문구와 문제 코드를 곧바로 질문으로 올리고, AI와 사람이 한 스레드에서 답하고 확인한다(Sentry·SonarQube 같은 연동).

이 구상은 결정 2·5와 정면으로 부딪힌다. 다만 구상 쪽이 더 강하다고 판단했다. 재현 증거는 AI 채팅이 줄 수 없는 것이고, AI의 약점인 환각은 실행으로 걸러낼 수 있기 때문이다. 대신 두 결정이 막으려던 위험(원본 훼손, 사람의 경험 데이터가 AI 생성물에 묻히는 것, 신뢰할 수 없는 코드 실행)은 조건으로 남겨야 한다.

## 결정 (Decision)

1. **엔진은 원본을 수정하지 않고 제안만 한다.** 질문 판본은 이미 append-only이고 QPR(ReviewRequest)과 Fork가 있다. 엔진은 QunoBot 주체로 별도 레이어(주석·제안·실행 기록)에만 쓰고, 작성자가 수락하면 그때 새 리비전이 된다. 엔진의 모든 산출물에는 출처, 입력 해시, 환경 이미지 다이제스트, 실행 로그 참조를 붙이고 작성자·열람자가 이의를 제기하면 재실행한다.
2. **격리된 재현 러너를 허용한다(ADR-0067 결정 5 대체).** 단계적으로 간다.
   - **1단계**: 사용자 저장소 + 외부 CI(GitHub Actions) 결과를 받는다. Quno가 코드를 실행하지 않는다.
   - **2단계**: 호스티드 샌드박스 제공자를 허용 생태계(JVM Gradle, Node)에만 쓴다.
   - **3단계**: 자체 호스팅은 2단계의 비용·제약이 임계를 넘을 때만 검토한다.
   - 공통 격리 요건: 네트워크 차단(패키지 미러 허용목록만), 시간·메모리·CPU 상한, 일회성 환경, 비밀값 없음, 사용자 쿼터와 신뢰 등급, 같은 코드+환경 해시는 결과 재사용, 새 릴리스 같은 이벤트 기준 재검증.
   - 결과는 `재현됨 / 재현 안 됨 / 빌드 실패 / 판단 불가` 4종으로 정직하게 표시한다. **"재현됨"은 정답이 아니다** — 재현 코드가 문제를 잘못 모사하거나 flaky일 수 있으므로 원시 로그를 항상 열람할 수 있게 한다.
3. **AI는 라벨 붙은 1차 응답자로 참여한다(ADR-0067 결정 2 수정).** 허용 조건은 다음과 같다.
   - AI 출력은 `Answer`가 아닌 별도 객체이고 화면에서 사람 답변과 구분된다. 사람 명의로 위장하지 않는다.
   - 러너 검증을 통과하거나 사람이 확인하기 전에는 평판·채택·Super Answer 대상에서 제외한다.
   - 사람이 수락해 리비전이나 `Answer`로 올릴 때는 그 사람 명의가 된다.
   - 사용자 데이터를 외부 모델에 보내는 조건(옵트인·마스킹·비용 상한)은 Phase 67의 정책을 따르고, 사용자·조직 단위로 끌 수 있다.
   - 기각한 대안: AI가 `Answer`로 직접 게시(사람 경험 데이터가 AI 생성물에 묻힘), AI 완전 배제(IDE 흐름의 즉시 응답을 포기).
4. **상태 전환은 계속 사람이 한다.** 엔진은 "깨짐 감지" 같은 증거 배지를 자동으로 붙이지만(오버레이), OUTDATED 같은 상태 전환은 사람의 승인으로만 일어난다([ADR-0033](0033-technology-version-scan-detection-only-no-auto-outdated.md) 유지). 이는 ADR-0067 결정 4와 같다.
5. **비공개 질문을 IDE 연동의 선행 조건으로 한다.** 지금 질문에는 공개 범위 개념이 없어 모두 공개다. 사내 코드를 올릴 수 있으려면 조직 비공개 질문과 "정제해서 공개" 흐름이 먼저 필요하다. 비공개 질문은 외부 모델 전송과 러너 실행 모두 기본 금지다.
6. **IDE 연동은 IntelliJ를 먼저, VS Code를 이후에 한다.** 첫 대상이 Kotlin/Spring 개발자이고 팀 스택도 Kotlin이다. 클라이언트는 얇게 두고 CLI/MCP(Phase 65)의 토큰·API를 공유한다. 업로드 전에 로컬 비밀값 스캔과 미리보기를 필수로 한다.

ADR-0067의 결정 1(Stack Fingerprint 우선), 3(AI 에이전트를 유통 채널로), 4(자동 판정 불확대), 6(좁은 콜드 스타트)은 그대로 유지한다.

## 결과 (Consequences)

- **비용과 보안이 상시 부담이 된다.** 러너 비용은 사용량에 비례하고, 악용(채굴 등)과 격리 우회가 상시 위험이다. 그래서 첫 슬라이스를 "단일 파일 Kotlin 스크립트 + 최소 Gradle 프로젝트, 버전 3~5개"로 좁히고 비용·성공률·flaky 비율·이의 비율을 계측한다.
- **Quno가 CI 회사가 될 위험이 있다.** 허용 생태계 한정, 단계적 도입, 자체 호스팅을 마지막으로 미루는 것이 이를 막는 장치다.
- **법적·약관 검토가 필요하다.** 사용자가 올린 코드를 실행·보관하는 것의 라이선스와 이용 약관은 러너 도입 전에 확인한다(사람이 할 일).
- **비공개 질문이 가장 큰 누수 위험이다.** 검색·피드·Flow·대시보드·관련 질문·Cluster·sitemap·OG와 전역 캐시(`@Cacheable`)에 비공개가 섞이지 않는지 전수 점검이 Phase 79의 핵심이다.
- **재검토 조건**: 월 러너 비용이 정한 상한을 넘을 때, 보안 사고가 있을 때, 재현 결과에 대한 사용자 이의 비율이 높아 신뢰 신호로 기능하지 못할 때 범위를 줄이거나 중단한다.
