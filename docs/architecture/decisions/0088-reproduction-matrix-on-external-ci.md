# ADR-0088: 버전 매트릭스는 외부 CI 위에서 먼저 — 호스티드 샌드박스는 전환 기준을 정해 두고 보류, 큐 대신 "실행할 차례인가"를 묻는 계획 API

- 날짜: 2026-11-02
- 상태: 승인됨

## 배경 (Context)

PLAN.md Phase 81은 "호스티드 샌드박스 러너 + 버전 매트릭스"다. Quno가 격리된 환경에서 사용자 코드를 직접 실행하고, 답변의 적용 범위 안에서 3~5개 버전으로 매트릭스를 펼친다.

호스티드 실행에는 사람이 정해야 할 것이 셋 있다.

- 실행 제공자
- 월 비용 상한
- 사용자 코드를 실행·보관하는 데 따른 라이선스·약관 확인

이번 단계에서 사용자에게 진행 방식을 물었고, **외부 CI 매트릭스를 먼저 만들고 호스티드 샌드박스는 보류**하기로 했다.

Phase 80(ADR-0087)으로 이미 다음이 갖춰져 있다.

- 사용자 저장소의 GitHub Actions가 Quno 재사용 워크플로로 실행한다.
- 결과를 OIDC 토큰으로 증명해 보낸다.

매트릭스, 우선순위, 결과 통합, 계측은 이 기반 위에서 Quno가 코드를 실행하지 않고도 만들 수 있다.

## 결정 (Decision)

### 1. 매트릭스는 캡슐의 한 패키지 버전 축이다

- 캡슐에 **매트릭스 패키지**(예: `com.zaxxer:HikariCP`)와 **꼭 돌릴 버전**(최대 5개)을 선택적으로 둔다(V37).
- Quno는 패키지별 릴리스 목록을 갖고 있지 않다(ADR-0033의 버전 스캔은 태그별 최신 버전 하나뿐). 그래서 질문이 이미 아는 버전에서 이 순서로, 최대 5개를 고른다.
  1. 작성자가 지정한 버전
  2. 질문 스택 지문의 버전(`^5.1.0`은 `5.1.0`으로 읽음, ADR-0076)
  3. 답변 적용 범위의 경계 `fromVersion`·`untilVersion`(ADR-0077). 답변이 "여기부터"·"여기까지"라고 말한 곳이 실행 결과가 가장 많은 것을 알려 주는 곳이다.
- 고른 버전은 버전 순으로 정렬한다. 패키지가 없거나 아는 버전이 하나도 없으면 칸은 하나다.
- 버전 축만 둔다. JDK 축은 캡슐의 `java-version` 하나로 둔다. 축을 둘로 늘리면 칸 수가 곱으로 늘어 사용자 CI 분을 빠르게 쓴다.
- 패키지별 릴리스 목록(Maven Central·npm 조회)은 이분 탐색(Phase 83)에 필요해질 때 따로 정한다.
- 빌드에 버전을 넣는 방법: 워크플로가 `QUNO_VERSION` 환경 변수와 Gradle 프로젝트 속성 `qunoVersion`(`ORG_GRADLE_PROJECT_qunoVersion`)을 넣는다.
  - 저장소 쪽 예: `implementation("com.zaxxer:HikariCP:${findProperty("qunoVersion") ?: "5.1.0"}")`
  - Dockerfile은 `--build-arg QUNO_VERSION`으로 받는다.
  - Quno가 빌드 파일을 고쳐 쓰는 방식은 기각한다. 생태계마다 다르고, 실행되는 것이 저장소에 보이는 것과 달라진다.

### 2. 큐 대신 계획 API: 워크플로가 실행 전에 묻는다

- PLAN의 "작업 큐, 조회수 기반 우선순위"는 Quno가 실행을 시작하는 구조를 전제로 했다.
- 외부 CI에서는 실행 시점을 저장소의 cron이 정한다. 그래서 큐 대신, 매일 도는 워크플로가 먼저 `POST /reproduction-runs/plan`으로 "지금 실행할 차례인가"를 묻는다.
  - 결과를 보낼 때와 같은 OIDC 토큰을 쓰고, 저장소와 고정 커밋도 같은 규칙으로 확인한다.
- **바로 실행하는 경우:** 수동 실행(`workflow_dispatch`·`push`·`pull_request`, 토큰의 `event_name`), 열린 이의 제기, 첫 실행
- **그 밖에는 마지막 실행 이후 간격이 지났을 때:** 조회 100회 이상이면 1일, 10회 이상이면 3일, 그 밖에는 7일
- 차례가 아니면 매트릭스를 비워 돌려주고, 워크플로는 계획 작업만 하고 끝난다(수 초).
- 응답에는 캡슐의 패키지 버전만 담고, 질문 내용은 담지 않는다. 비공개 질문(ADR-0085)이어도 그 저장소의 토큰을 가진 쪽만 받는다.

### 3. 결과 통합: 질문의 매트릭스 표

- 실행은 매트릭스 칸(환경 × 버전)과 시작 이벤트를 함께 기록한다.
- 질문 화면은 칸별 최신 결과를 **버전(행) × 환경(열)** 표로 보여 준다. 계획에 있지만 아직 결과가 없는 버전도 빈 행으로 남겨, 빈 칸이 보이게 한다.
- "다음 정기 실행 N일 후"를 함께 표시한다.
- PLAN 81.3은 답변 쪽 표시도 말한다. 그 부분은 Phase 72(사용자 확인 "아직 돼요·이제 안 돼요")가 답변 적용 범위에 결과를 붙일 때 함께 한다. 러너 결과와 사람의 확인을 구분해 표시하는 것도 그때 정한다.

### 4. 계측

`GET /metrics/reproduction`(로그인 사용자, `/metrics`와 같은 공개 수준)은 최근 30일을 집계한다.

- 실행 수
- 판정이 난 실행 수(재현됨·재현 안 됨)
- 신뢰 워크플로 실행 수
- 러너 분
- 칸 수와 flaky 칸
- 활성 캡슐 수
- 이의 제기 누적 수

세부 기준

- **flaky 칸:** 같은 칸·같은 커밋에서 "재현됨"과 "재현 안 됨"이 모두 나온 칸
- **건당 비용:** 외부 CI에서는 Quno 비용이 0이다. 대신 저장소들이 쓴 러너 분을 센다. 호스티드로 넘어갈 때 비용을 추정하는 근거가 된다.
- **이의 제기 수:** 이의 제기는 다음 실행이 닫으므로, 사라지지 않게 캡슐에 누적 횟수를 둔다.

### 5. 호스티드 샌드박스는 보류하고 전환 기준만 정한다(81.1·81.5)

다음 중 하나가 **3개월 연속** 관측되면 호스티드 샌드박스 착수를 다시 검토한다.

- 캡슐을 붙이려다 포기하는 비율이 높다. 정확히는, 재현 코드를 공개 저장소에 둘 수 없다는 이의나 요청이 활성 캡슐의 20%를 넘는다.
- 매트릭스 요청이 GitHub 호스티드 러너가 줄 수 없는 환경(특정 OS·아키텍처)을 월 50건 넘게 요구한다.
- 질문 코치(Phase 84)의 "제출 전 재현"처럼 저장소 없이 실행해야 하는 기능을 실제로 착수하기로 한다.

착수할 때 사람이 먼저 정할 것

- 제공자
- 월 비용 상한
- 약관(사용자 코드 실행·보관, 로그 보관 기간)

그때의 격리 요건은 PLAN 81.1 그대로다.

- 네트워크 차단과 패키지 미러 허용목록
- 시간·메모리·CPU 상한
- 일회성 환경
- 비밀값 없음
- 결과 캐시 키(코드 + 환경 해시)

**자체 호스팅(3단계):** 호스티드 비용이 월 상한의 80%를 3개월 넘게 쓰거나, 제공자 제약(실행 시간·이미지) 때문에 거절된 실행이 10%를 넘을 때만 검토한다.

## 결과 (Consequences)

- 82(신규 릴리스 회귀 감시), 83(이분 탐색), 84(질문 코치)는 PLAN에서 81을 선행으로 둔다. 이 중 82·83은 같은 외부 CI 기반 위에서 진행할 수 있다.
  - 82: 새 릴리스를 감지하면 해당 캡슐을 "차례"로 만들고 매트릭스에 그 버전을 넣는 방식
  - 83: 계획 API가 다음에 확인할 버전을 고르는 방식
- 84.1(제출 전 백그라운드 재현)은 저장소가 없는 단계라 호스티드 실행이 필요하다. 위 전환 기준의 세 번째 항목에 해당한다.
- 사용자는 저장소 빌드에 `qunoVersion` 한 줄을 넣어야 매트릭스를 쓸 수 있다. 화면의 설정 안내와 워크플로 설명에 적어 두었다.
- 매일 도는 cron이 차례가 아닐 때는 계획 작업만 돈다. 그래서 사용자 CI 분은 조회가 많은 질문에 몰린다.
- 검증
  - `ReproductionPlanTest`: 버전 선택 순서·상한·정렬, 간격 규칙, 칸 검사
  - `ReproductionRunE2ETest` 매트릭스 시나리오: 계획(첫 실행·차례 아님·수동·이의 제기), 다른 저장소 409, 위조 401, 칸별 기록, 잘못된 버전 409, 패널 표, 지표
  - 브라우저: 화면에서 매트릭스 설정 → 로컬 발급자 토큰으로 계획·5칸 보고 → 표와 다음 실행 시각 표시
