# ADR-0047: 테스트 — 회원가입 UI 신설, E2E/부하 테스트 범위

- 날짜: 2026-09-10
- 상태: 승인됨

## 배경 (Context)

상용 전환 체크리스트([production-readiness.md](../../product/production-readiness.md) B-5)에 따라 배포·보안·관측 가능성·신뢰성에 이어 테스트를 진행한다. E2E 테스트의 핵심 골든 패스(회원가입→질문 작성→답변)를 준비하던 중, 프론트엔드에 **회원가입 화면이 아예 없다**는 것을 발견했다 — `authApi.signUp`은 정의만 되어 있고 어디서도 호출되지 않았고, `/login` 페이지와 `AppHeader` 어디에도 가입으로 가는 링크가 없었다. 지금까지 실제로는 아무도 웹사이트를 통해 계정을 만들 방법이 없었던 셈이다.

## 결정 (Decision)

1. **회원가입 화면을 이번에 함께 만든다.** 원래는 "테스트" 항목이었지만, E2E 테스트를 작성하려면 어차피 이 화면이 필요했고, 이건 "상용 제품"이 성립하기 위한 훨씬 근본적인 격차라 별도 Phase로 미루지 않고 바로 고쳤다. `/signup`(신규, `/login`과 동일한 패턴)과 `useSignUp`(신규 — 가입 성공 시 `useLogin`을 재사용해 바로 로그인까지 이어감)을 추가하고, `/login`과 `AppHeader`(로그아웃 상태)에 상호 링크를 달았다.
2. **E2E는 Playwright로, 결제 없는 핵심 플로우만 다룬다.** `frontend/e2e/golden-path.spec.ts`가 회원가입→질문 작성→답변까지를 실제 UI로 검증한다. Direct Ask 유료 결제(ADR-0037)는 범위에서 뺐다 — 토스페이먼츠 호스팅 체크아웃으로 리다이렉트되는 플로우라 안정적으로 자동화하려면 결제사 테스트 페이지의 DOM에 의존하게 되어 깨지기 쉽고, 이 프로젝트가 통제할 수 있는 영역 밖이다. `@playwright/test`/`@testing-library/*`가 이미 devDependencies에 설치돼 있었지만(누가 언제 넣었는지 불명) 설정 파일도 테스트도 전혀 없었다 — 이번에 처음 실제로 연결했다.
3. **Vitest와 Playwright의 테스트 파일을 디렉터리로 분리한다.** `e2e/**`를 vitest 기본 include 패턴이 함께 집어가면서 `npm test`가 Playwright의 `test()`를 vitest의 것으로 착각해 충돌하는 것을 발견해, `vitest.config.ts`에 `exclude: ["e2e/**"]`를 추가했다.
4. **CI에 `e2e` 잡을 추가한다.** 백엔드(docker-compose 인프라 + bootRun)와 프론트엔드(dev 서버)를 모두 띄운 뒤 Playwright를 실행한다 — 부하 테스트와 달리 E2E는 로컬 docker-compose 스택으로도 의미 있는 신호(플로우 자체가 깨졌는지)를 준다고 판단했다.
5. **부하 테스트는 스크립트만 준비하고 실행은 보류한다.** `scripts/load-test.js`(k6)가 비로그인 공개 읽기 경로(검색/태그 목록/질문 상세)에 대해 VU 수·기간을 환경변수로 받는 램핑 시나리오를 정의한다. 로그인이 필요한 쓰기 경로는 VU마다 계정을 발급/관리해야 해서 범위 밖으로 뺐다. 로컬 docker-compose(Postgres/Redis 한 대짜리)에 대고 돌려서는 병목이 실제 인프라 사이징이 아니라 이 개발 머신 자체가 되기 쉬워, 스크립트가 문법적으로 동작하는지만 짧게(VUs=3, 10초) 스모크 테스트했다 — 목표 동시접속 규모에 대한 실제 응답시간·에러율 측정은 스테이징 인프라(사람이 할 일, production-readiness.md A)가 갖춰진 뒤로 미룬다.

## 결과 (Consequences)

- 회원가입 화면이 생겼으니, 로그인 화면처럼 앞으로 이 화면에도 컴포넌트를 추가할 때는 `redirectTo` 쿼리 파라미터 패턴을 유지해야 한다.
- Direct Ask 결제 플로우는 E2E로 커버되지 않는다 — 회귀가 생기면 여전히 수동 검증이나 백엔드 통합 테스트에 의존한다.
- `scripts/load-test.js`의 스모크 실행 결과(로컬 기준 p95 57ms)는 실제 용량 산정 근거가 아니다 — 스테이징에서 재실행하기 전까지는 참고용도 아니다.
- 프론트엔드 유닛 테스트가 1개에서 6개 파일(18개 테스트)로 늘었지만, 여전히 대부분의 컴포넌트/훅은 테스트가 없다 — 이번 Phase는 "극단적 불균형 완화"이지 "충분한 커버리지 확보"가 아니다.
