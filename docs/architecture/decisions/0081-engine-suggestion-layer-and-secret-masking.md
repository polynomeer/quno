# ADR-0081: 엔진 제안 레이어 — 원본은 그대로 두고 제안만 저장, 수락하면 작성자 명의 리비전, 비밀값은 읽을 때 작성자 외에게 가린다

- 날짜: 2026-11-01
- 상태: 승인됨

## 배경 (Context)

[ADR-0068](0068-living-engine-runner-and-ai-first-responder.md) 결정 1은 엔진이 원본을 수정하지 않고 제안만 한다고 정했다. PLAN.md Phase 78은 이 원칙을 코드로 만드는 기반이다. 첫 엔진 기능은 실행이 필요 없는 두 가지다.

- **비밀정보 탐지(78.4):** 질문 로그·본문에 붙여 넣은 키·토큰은 지금 그대로 공개된다.
- **정리 제안(78.5):** 다음 PR에서 다룬다.

78.1이 정할 것은 다음과 같다.

- 산출물 모델과 출처 필드
- QunoBot 주체
- 수락하면 리비전이 되는 경로
- 이의 제기
- 작업 큐와 예산

## 결정 (Decision)

### 산출물 모델: `engine_suggestions` + `engine_runs`

- **제안(`engine_suggestions`):** 질문 하나의 특정 판본에 대한 고칠 거리 하나다.
  - 종류(`kind`)와 상태(`OPEN`/`ACCEPTED`/`DISMISSED`/`SUPERSEDED`)
  - 대상 판본 번호
  - 사람이 읽을 요약과 근거(JSON)
  - 수락했을 때의 내용(`proposed_title`·`proposed_body`·`proposed_environment`·`proposed_logs`). `null`이면 그 필드는 그대로 둔다.
  - 처리 시각과 처리한 사람
- **출처 필드(ADR-0068)**는 모든 제안에 붙는다.
  - `engine`(예: `secret-scan`), `engine_version`
  - `input_hash`: 읽은 제목·본문·환경·로그의 SHA-256
  - `env_digest`, `log_ref`: 실행하는 엔진(러너, Phase 80)이 채운다. 지금 엔진은 `null`이다.
- **실행 기록(`engine_runs`):** 질문·판본·엔진·엔진 버전·입력 해시·발견 수·시각.
  - 같은 입력을 다시 분석하지 않게 하는 멱등 키 역할을 한다.
  - 기존 질문을 훑는 기준이기도 하다. "이 엔진 버전으로 최신 판본을 본 적이 없는 질문"을 찾는다.
- **원본은 손대지 않는다.** 질문 판본은 append-only 그대로다.

### QunoBot 주체와 수락 경로

- QunoBot은 사용자 계정이 아니다. `engine` 출처 필드로만 식별한다. 사람 계정으로 위장하지 않으며, 평판·투표·알림의 행위자도 아니다.
- **수락하면 작성자 명의로 새 리비전이 된다.** 기존 `ReviseQuestionUseCase`를 작성자를 행위자로 해서 그대로 부른다. 그래서 판본 이력·diff·Ward 알림·에러 시그니처 재색인이 사람이 직접 고친 것과 똑같이 동작한다.
- **ReviewRequest(QPR)는 재사용하지 않는다.** ReviewRequest는 "사람이 사람에게 정보를 요청하는" 모델이고 제안할 본문을 담지 않는다. 엔진 제안은 바뀐 내용을 들고 있어야 한다.
- 수락 시점에 질문이 이미 다른 판본으로 넘어갔으면 409를 돌려주고 제안을 `SUPERSEDED`로 바꾼다. 질문이 수정되면 이전 판본의 열린 제안도 모두 `SUPERSEDED`가 된다. 엔진은 새 판본을 다시 분석해 필요하면 새 제안을 만든다.
- 제안은 **질문 작성자에게만 보이고**, 수락·무시도 작성자만 한다. 공개 화면에는 아래의 마스킹만 드러난다.

### 이의 제기

- 실행이 없는 엔진은 결정적이다. 다시 돌려도 결과가 같으므로 "재실행으로 판정"하는 이의 제기는 의미가 없다.
- 그래서 지금의 이의 제기는 **작성자의 무시(`DISMISSED`)**다.
  - 비밀값 제안을 무시하면 "비밀값이 아니다"라는 뜻이다. 그 값들의 해시를 질문별 허용 목록(`engine_secret_allowlist`)에 넣고, 이후 판본에서도 가리지 않는다.
- 열람자의 이의 제기와 재실행은 결과가 흔들릴 수 있는 러너(Phase 80)에서 정한다.

### 작업 실행: 동기 분석 + 상태 기반 스윕

- **질문 작성·수정·Fork 트랜잭션 안에서 동기로 분석한다.**
  - 에러 시그니처 색인(ADR-0075)과 같은 자리다. 정규식 몇 개라 비용이 작다.
  - 작성자가 게시 직후 바로 경고를 봐야 한다.
- **기존 질문은 스케줄러가 훑는다.** `engine_runs`에 현재 엔진 버전 기록이 없는 질문의 최신 판본을 주기마다 일정 수(기본 50)만 분석한다. 엔진 버전을 올리면 전체가 자연히 다시 분석된다.
  - Outbox를 재사용하지 않는다. Outbox는 "일어난 일"의 기록인데, 기존 질문 백필은 일어난 일이 없다.
  - 별도 작업 큐 테이블도 두지 않는다. 할 일은 상태(분석 기록의 유무)로부터 계산할 수 있다.
  - 스케줄러는 `OutboxDispatchScheduler`처럼 프로퍼티로 끌 수 있고, 테스트에서는 끈다([ADR-0072](0072-disable-outbox-dispatch-scheduler-in-tests.md)).
- 예산과 우선순위가 정말 문제가 되는 것은 실행 비용이 큰 러너다. 그래서 작업 큐 테이블은 Phase 80에서 도입한다.

### 비밀정보 탐지와 마스킹(78.4)

- **탐지:** 도메인의 `SecretDetector`가 제목·본문·환경·로그에서 찾는다. 대상은 다음과 같다.
  - 형식이 분명한 키: AWS 액세스 키, GitHub·Slack·Stripe·Google API 토큰, Quno 개인 액세스 토큰, PEM 개인 키, JWT
  - URL에 박힌 비밀번호(`scheme://user:password@host`)
  - `password=`·`secret=`·`token=`·`api_key=` 같은 대입문의 값. 엔트로피가 3.0 이상이고 8자 이상일 때만 잡는다. `password=changeme` 같은 예시 값은 오탐하지 않으려는 것이다.
  - 공인 IPv4 주소. 사설·루프백·문서용 대역은 제외한다.
- **마스킹은 읽을 때 한다.**
  - 질문 작성자가 아닌 사람에게는 찾은 부분을 `[가려짐: AWS 액세스 키]`처럼 바꿔서 응답한다.
  - 대상 경로는 질문 상세, 판본 조회, 판본 diff, 판본 목록의 제목이다. Fork는 원 질문의 내용을 가린 채로 복사한다(원 작성자 본인의 Fork는 제외).
  - 저장된 원본은 작성자에게 그대로 보인다(PLAN 78.4).
  - 읽을 때 계산하므로 탐지 규칙을 고치면 과거 판본에도 바로 적용된다.
  - 허용 목록에 든 값은 가리지 않는다.
- **제안:** 가릴 것이 있으면 `SECRET_REDACTION` 제안을 만든다.
  - 수락하면 비밀값을 `[REDACTED]`로 바꾼 새 리비전이 된다.
  - 그래도 과거 판본에는 원본이 남는다. 그래서 화면에서 "키를 폐기·교체하세요"라고 안내한다.
  - 새 비밀값 제안이 생기면 작성자에게만 알림(`ENGINE_SECRET_DETECTED`)을 보낸다. Ward 구독자에게는 보내지 않는다.
- **이번 범위 밖:** 답변·댓글의 비밀값. 같은 탐지기를 붙일 수 있지만 수락 경로(답변 리비전)가 달라 다음 단계로 미룬다.
- **목록의 제목은 가리지 않는다.** 검색·피드·관련 질문 같은 요약 목록의 제목까지 가리려면 목록 조회 경로마다 탐지를 돌려야 한다. 제목에 키를 넣는 경우는 드물고, 상세 화면의 제목은 가린다. 실제로 발견되면 그때 요약 조립기(`QuestionSummaryHydrator`)에 붙인다.

## 결과 (Consequences)

- 이미 공개된 질문의 키·토큰도 다음 스윕부터 작성자 외에게 가려진다.
- 마스킹은 요청마다 정규식을 돌리는 비용이 든다. 질문 상세는 캐시하지 않는 경로라 영향이 작다. 다만 판본 diff처럼 텍스트가 큰 경로는 계측 대상이다.
- 오탐은 공개 화면에서 내용을 가리는 쪽으로 실패한다. 작성자는 무시로 풀 수 있고, 열람자는 작성자에게 댓글로 알릴 수 있다. 미탐은 지금과 같다(그대로 공개).
- 제안 모델이 내용을 통째로 들고 있어 저장 공간이 판본 하나만큼 늘어난다. 그 대신 수락이 기존 리비전 경로 하나로 끝난다.
