# ADR-0079: 개인 액세스 토큰 — 해시만 저장하는 `quno_pat_` 토큰, READ·ASK 두 스코프, 토큰 관리는 브라우저 세션에서만, 토큰 단위 레이트리밋

- 날짜: 2026-10-28
- 상태: 승인됨

## 배경 (Context)

Phase 65는 CLI와 MCP 서버로 Quno를 터미널·IDE·코딩 에이전트 안으로 가져간다. 그런데 지금 인증은 로그인으로 받는 JWT뿐이다.

- 액세스 토큰은 수명이 짧고 리프레시 흐름을 전제로 한다. 셸 스크립트나 MCP 설정 파일에 넣어 둘 수 없다.
- 레이트리밋은 로그인·회원가입 같은 일부 경로에 IP 단위로만 걸려 있다([production-readiness.md](../../product/production-readiness.md) B-2). 자동화된 클라이언트가 API를 계속 부르면 막을 장치가 없다.

PLAN.md 65.1(인증 설계)과 65.4(남용 방지)가 이 문제를 다룬다.

## 결정 (Decision)

### 토큰 형식과 저장

- 형식은 `quno_pat_` + 32바이트 난수(base64url)다. 접두사가 있으면 비밀 스캐너(GitHub secret scanning 등)가 유출을 찾기 쉽고, 필터가 JWT와 구별하기도 쉽다.
- **SHA-256 해시만 저장한다.** 원문은 발급 응답에서 한 번만 보여준다.
  - 비밀번호와 달리 엔트로피가 충분히 높아 BCrypt 같은 느린 해시가 필요 없다.
  - 요청마다 조회해야 하므로 빠른 해시가 맞다.
- 화면 식별용으로 원문 앞 12자(`quno_pat_ab…`)를 따로 저장한다.
- 만료는 30·90·365일 중에서 고른다. 기본 90일이고, 무기한은 두지 않는다.
- 사용자당 유효한 토큰은 10개까지다.
- `last_used_at`은 5분 이상 지났을 때만 갱신한다. 요청마다 쓰기가 생기지 않게 하기 위해서다.

### 스코프

| 스코프 | 허용 범위 |
|---|---|
| `READ` | 모든 `GET`, 그리고 아무것도 저장하지 않는 미리보기 `POST`(`/error-signatures/preview`, `/stack-fingerprints/parse`) |
| `ASK` | 질문 작성(`POST /questions`)과 수정(`POST /questions/{id}/versions`) |

- 토큰으로 들어온 요청은 스코프 밖이면 **403**이다. 투표, 답변, 채택, 모더레이션, 결제, 계정 설정은 토큰으로 할 수 없다.
- 이후 쓰기 도구(Phase 92·93·95)가 필요해지면 그때 스코프를 늘린다.
- **토큰 관리(`/me/tokens`)는 토큰으로 할 수 없다.** 유출된 토큰이 스스로 새 토큰을 발급해 폐기를 피하는 경로를 막는다. 발급·폐기는 로그인한 브라우저 세션(JWT)에서만 한다.
- 스코프 판정은 인증 필터에서 끝낸다. 컨트롤러마다 어노테이션을 다는 방식은 새 엔드포인트가 생길 때 빠뜨리기 쉽다. 허용 목록 방식이라 빠뜨려도 막히는 쪽으로 실패한다.

### 토큰 단위 레이트리밋(65.4)

- 토큰으로 들어온 요청에 토큰별 인메모리 버킷을 건다. 기본 분당 120회이고 프로퍼티로 바꿀 수 있다.
- 기존 IP 버킷과 같은 Bucket4j를 쓴다. 단일 인스턴스 한계도 같다(다중 인스턴스에서는 Redis로).
- JWT 요청에는 이번에 걸지 않는다. 브라우저 사용 패턴의 기준선이 없어서 적절한 한도를 정할 근거가 없다.
- **응답 크기 상한은 MCP 서버(65.3)에서 다룬다.** 에이전트에 넘길 출력을 자르는 것이 목적이라, API 공통 제한보다 도구 쪽에서 자르는 편이 맞다.

## 결과 (Consequences)

- CLI와 MCP 서버가 쓸 인증 수단이 생긴다. 토큰은 사용자 권한의 일부만 갖는다.
- 허용 목록이 엔드포인트 경로를 알고 있어야 한다. 그래서 새 읽기 전용 `POST`를 토큰으로 열려면 목록에 추가해야 한다.
- 폐기는 즉시 반영된다. 매 요청마다 해시로 DB를 조회하기 때문이다(인덱스 조회 한 번). 캐시를 두지 않은 대가로 요청당 쿼리가 하나 늘어난다.
